# sneaky-reader

一个极简的桌面小说阅读器。**无标题栏、无系统托盘、不支持文字选中**，只有一个可自由调整大小的纯文字阅读窗口，所有行为由 `config.yaml` 驱动。

## 特性

- **配置驱动**：所有设置集中在 `config.yaml`，文件内自带中文注释，无需任何可视化设置界面。
- **来源灵活**：可指定单个 txt、多个 txt，或一个目录（目录下 txt 按文件名自然顺序合并）。
- **自动章节解析**：自动识别 `第一章 标题` / `第2015章 标题` 形式的章节，跳过书名、作者等书头信息。
- **逐行滚动**：键盘 `↑` / `↓` 与鼠标滚轮按行滚动；`PageUp` / `PageDown` 切换上一章 / 下一章。
- **进度记忆**：自动把「章节 + 段落」进度写回 `config.yaml`，重开后精确恢复。
- **窗口状态记忆**：关闭、拖动或缩放结束时自动记录窗口的位置与尺寸，下次启动原样恢复（显示器变更导致坐标失效时自动回退到 `position` 重新定位）。
- **窗口行为**：无标题栏；按住窗口内区拖动即可移动；**左键双击关闭**；边缘可缩放。
- **宽度重排**：改变窗口宽度后文字自动重排，并保持停留在当前章节。
- **7 套阅读主题 / 字体可配**：低蓝光、对比度适中的配色（见下表），字体族与字号可配。
- **可选半透明毛玻璃**：配置 `window.opacity` 让窗口半透明，`window.blur` 开启 Windows 11 系统级高斯模糊（默认均关闭，即完全不透明）。
- **正则替换**：用 `config.yaml` 里的正则规则列表调整「显示出来的文字」（去网站广告、去字数标记等），**txt 文件本身不会被修改**。

## 环境要求

- Node.js 18+（建议 20+）
- Windows / macOS / Linux 桌面环境

## 安装与运行

```bash
npm install
npm start
```

首次运行若无 `config.yaml`，程序会自动生成一份带注释的默认模板。

> 在 PowerShell 里运行 `npm run dev` 时，中文日志可能显示为乱码（如 `涓婚=gray`）。这是终端编码问题，不影响程序本身，解决办法见[常见问题](#powershell-里运行-npm-run-dev-时中文日志乱码)。

## 打包为 exe

```bash
npm run build        # 产出单个 exe：dist/sneaky-reader-<版本号>-portable.exe
npm run build:dir    # 可选：只产出免安装文件夹 dist/win-unpacked/，便于本地快速验证
```

产物**只有一个 exe**（约 70 MB），双击即用，无需安装。

### 打包后的文件布局与路径规则

- **`config.yaml` 就在 exe 旁边**，直接编辑即可（`app.asar` 内部是只读的，不能放配置）。单文件便携版运行时会被解压到系统临时目录，程序通过 `PORTABLE_EXECUTABLE_DIR` 把配置写到**便携 exe 真正所在的位置**，而不是临时目录。
- **小说资源不打进 exe**，完全由你在 `config.yaml` 里指定：
  - **绝对路径**：按该路径读取，与 exe 放在哪无关
  - **相对路径**：以 `config.yaml` 所在目录为基准，也就是「exe 旁边」

```yaml
source: D:/小说/我的小说.txt   # 绝对路径
source: novels/我的小说.txt    # 相对路径 → <exe 所在目录>/novels/我的小说.txt
source: D:/小说               # 目录 → 目录下所有 .txt 按文件名自然顺序合并
```

### 路径有问题时会直接提示

提示会显示在阅读窗口里，并回显**解析后的路径**与**配置文件位置**，窗口可滚动查看完整内容：

```
读取失败：路径不存在：D:/不存在的目录/没有这本小说.txt

请在 config.yaml 中把 source 改成你自己的小说路径：
  · 单个文件：source: D:/小说/我的小说.txt
  · 一个目录：source: D:/小说      （目录下所有 .txt 按文件名顺序合并）
  · 相对路径以配置文件所在目录（exe 旁边）为基准

配置文件：D:\your-folder\config.yaml
```

以下情况都会给出对应提示：`source` 留空、路径不存在、目录下没有 `.txt` 文件。

### 应用图标

图标文件固定在 `build/icon.png`：

- 要求**正方形**、边长 **≥ 256**（推荐 `512×512`），建议带透明通道。打包时 electron-builder 会自动转成多尺寸 ICO 并嵌进 exe。
- 换图标：直接替换 `build/icon.png` 后重新 `npm run build` 即可。
- 若自备多尺寸 `.ico`（16/32/48/64/128/256），放到 `build/icon.ico` 会被优先使用，效果比自动转换更可控。
- `npm start`（开发模式）跑的是 `electron.exe`，所以 `src/main.js` 里额外给窗口传了同一个图标，开发时任务栏图标也保持一致；该文件已通过 `files` 一并打进包里，保证打包后路径同样可解析。

> 打包用 `electron-builder`，配置写在 `package.json` 的 `build` 字段里。当前只针对 Windows x64。

## 配置说明（config.yaml）

| 配置项 | 说明 | 默认值 |
| --- | --- | --- |
| `source` | **必填**。小说来源：单个文件 / 文件数组 / 目录。相对路径以配置文件（exe）所在目录为基准 | 空 |
| `theme` | 阅读主题，见下方主题表 | `dark` |
| `fontFamily` | 字体族，逗号分隔按序回退 | `SimSun, Times New Roman, serif` |
| `fontSize` | 正文字号（px） | `10` |
| `lineHeight` | 行高倍数，同时决定逐行滚动步长 | `1.7` |
| `replace` | 正则替换规则列表，用于调整显示内容（只改显示，不改文件），见下节 | `[]` |
| `window.width` | 初始窗口宽度（px） | `400` |
| `window.height` | 初始窗口高度（px） | `160` |
| `window.position` | 首次启动位置：`top-left` / `top-right` / `bottom-left` / `bottom-right` / `center` | `top-left` |
| `window.opacity` | 窗口不透明度，`0.3` ~ `1`（`1` 为完全不透明） | `1` |
| `window.blur` | 半透明高斯模糊（Windows 11 亚克力材质），仅在 `opacity < 1` 时可见 | `false` |
| `remember.window.x` / `y` | 上次关闭时的窗口坐标，**程序自动写入** | 空 |
| `remember.window.width` / `height` | 上次关闭时的窗口尺寸，**程序自动写入** | 空 |
| `progress.chapter` | 当前章节索引（从 0 开始），**程序自动写入** | `0` |
| `progress.paragraph` | 章节内段落索引（从 0 开始），**程序自动写入** | `0` |

### 初始默认设置 vs 记忆配置

配置文件里刻意把两类值分开存放，互不覆盖：

- **`window`（初始默认设置）**：你手写的值，程序**从不修改**。首次启动、或删除了对应记忆项时生效。
- **`remember`（记忆配置）**：程序自动写入的窗口位置与尺寸。存在时优先于 `window`。

例如：`window.width: 400` 始终保留，而你缩放成 520 后关闭，程序只写 `remember.window.width: 520`。想回到 400，删掉那一行（或整个 `remember` 块）即可；也可以把 `remember.window.width` 改成你想要的任意值。

```yaml
window:            # 初始默认设置（你手写，程序不动）
  width: 400
  height: 100
  position: top-left

remember:          # 记忆配置（程序自动写入）
  window:
    x: 300
    y: 200
    width: 520
    height: 160
```

> 位置与尺寸单独判定：只记忆了尺寸、没有坐标时，位置仍按 `position` 定位，尺寸用记忆值。

### 正则替换（调整显示内容）

在不改动 txt 文件的前提下，用正则规则调整「显示出来的文字」，用来去掉网站广告、字数标记、分隔符之类的干扰内容。

```yaml
replace:
  - pattern: '^[\s　]*(请收藏本站|手机用户请浏览|天才一秒记住).*$'   # 整行的网站广告
    replace: ''
  - pattern: '[（(]本章完[）)]'                                     # 段尾或整行的「（本章完）」
    replace: ''
  - pattern: '[\s　]*[（(]\d{1,4}[）)][\s　]*$'                      # 段尾的（字数标记）
    replace: ''
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `pattern` | 是 | 正则表达式。建议用**单引号**包裹，这样 `\s`、`\d` 等反斜杠不会被转义 |
| `replace` | 否 | 替换成的文本；省略表示直接删除匹配到的内容 |
| `flags` | 否 | 正则标志；**省略时默认为 `g`**（替换全部匹配），常用 `i` 忽略大小写 |

行为说明：

- 规则**按书写顺序依次应用**，上一条的输出是下一条的输入。
- 规则应用到**章节标题与正文段落**；只改显示，不改文件。
- 某段被替换后**只剩空白时就整段隐藏**，不会留下一行空白（整行广告被删掉后，那一行会直接消失）。
- 替换文本中可用 `$1`、`$2` 引用捕获组，`$&` 代表整个匹配，`$$` 表示字面量 `$`。例如给章节号加空格：`pattern: '第(\d+)章'` 配 `replace: '第 $1 章'`。
- 最多 200 条；**写错正则的那一条会被忽略**（并在控制台提示），不影响其它规则，也不会导致程序打不开。
- **不影响章节识别与阅读进度**：章节解析与段落序号始终基于原始文本，因此增删规则后重开，进度仍指向同一段原文。

## 常见问题

### PowerShell 里运行 `npm run dev` 时中文日志乱码

现象：日志里的中文变成 `涓婚=gray 灏哄=556x224`、`宸插惎鐢? 1 鏉℃浛鎹㈣鍒?` 这类字符。

**原因**：Node / Electron 与 Chromium 的日志一律输出 **UTF-8** 字节；而 Windows PowerShell 5.1 在解码原生命令的输出时，用的是 `[Console]::OutputEncoding`，中文系统上默认是 **GB2312 / GBK（代码页 936）**。于是 UTF-8 字节被按 GBK 解释，就成了乱码。`npm run dev` 还会再套一层管道，所以日志必然经历这一步解码。

**解决办法**（任选其一）：

```powershell
# 1) 只对当前会话生效：先设置编码，再启动
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
npm run dev

# 2) 一劳永逸：写入 PowerShell 配置文件，之后每次打开都正常
if (!(Test-Path $PROFILE)) { New-Item -Path $PROFILE -ItemType File -Force | Out-Null }
Add-Content -Path $PROFILE -Value '[Console]::OutputEncoding = [System.Text.Encoding]::UTF8'
```

其它可选做法：

- 用 **Windows Terminal + PowerShell 7**——两者默认就是 UTF-8，无需任何设置。
- 在 **cmd.exe** 里先执行 `chcp 65001`，再跑 `npm run dev`（cmd 直接按控制台代码页渲染，改代码页即可生效）。
- 已验证的一个坑：把 `chcp 65001` 写进 npm 脚本**对 PowerShell 5.1 无效**。`chcp` 只改控制台代码页，不会更新 PowerShell 已缓存的 `[Console]::OutputEncoding`（实测执行后仍是「简体中文(GB2312)」），而 PowerShell 解码子进程输出用的正是后者。

> 该问题仅影响控制台的显示效果：`config.yaml`、小说文件与日志内容本身都是正确的 UTF-8，读写不受任何影响。

## 设计取舍

- **拖动区避开窗口边缘**：无边框窗口四周存在系统不可见的缩放边缘（约 8px，四角 16px）。拖动区因此收缩到窗口内区（边缘 16px 保留给系统缩放），避免按下时 Windows 同时进入原生缩放循环与拖动逻辑。
- **拖动用主进程光标绝对定位并锁定尺寸**：位置由主进程 `screen.getCursorScreenPoint()` 计算（与窗口同一坐标系），并以按下瞬间的窗口位置为基准做绝对定位；移动时使用 `setBounds` 显式携带按下瞬间的宽高。在 125% 等非 100% 缩放的 Windows 上，`setPosition` 会因 DPI 换算让窗口尺寸**逐步膨胀**，必须锁定尺寸才能避免。
- **按章节窗口渲染**：全书可达 14 万段，一次性渲染会拖慢启动并导致滚动位置漂移。因此只渲染当前章节附近 5 章，跨出边界时以「像素偏移」为锚点无缝切换窗口。
- **正则替换放在渲染层而不是解析层**：规则只作用于「渲染出来的文字」，章节数组与段落序号始终是原始数据。这样增删规则不会让阅读进度错位（进度 = 章节 + 段落索引），也不会因为规则改掉了「第X章」而破坏章节识别；代价是每次只处理当前窗口内的几百个段落，可以忽略。被规则清空的段落渲染时直接跳过（不留空行），其序号仍然保留，锚点定位会自动向前回退到最近的可见段。
- **不使用 `requestAnimationFrame` 做滚动节流**：窗口被遮挡时 rAF 会被挂起，导致锚点不再更新；改用基于时间的节流。
- **不使用 `-webkit-app-region: drag`**：它会吞掉双击与滚轮事件，与「双击最小化」「滚轮翻行」冲突。
- **写回配置采用定向文本替换**：进度只替换 `progress` 块，窗口状态只替换 `remember` 块，`window` 初始默认设置与你手写的注释、排版都被完整保留，而不是整文件重新序列化。
- **块的说明注释与块体分开写入**：`remember` 的说明注释不随块体一起重写，替换范围只覆盖块体本身（并会把紧邻上方的注释规整为一份）。否则每保存一次就会多插一份说明注释，导致文件里注释不断堆积。写入因此是幂等的：连续保存 N 次，文件内容始终保持一致。
- **初始默认设置与记忆配置分离**：程序只写 `remember`，所以你手写的 `window` 期望值不会被运行结果覆盖，任何时候都能对照或回退。
- **记忆配置优先于 `position`，但做了失效校验**：记录的坐标若已不可见（换显示器、拔掉副屏），自动按 `position` 重新定位，避免窗口跑到屏幕外。
- **底部位置以「工作区」为基准**：用 `screen.getPrimaryDisplay().workArea` 而非 `bounds`，它已扣除 Windows 任务栏占用的区域，因此左下 / 右下不会被任务栏遮挡；再加一次夹取，保证窗口完整落在工作区内。
- **窗口坐标与尺寸都对齐到「整数物理像素」网格**：在 125%（5/4）等非整数缩放下，DIP 值落在半个物理像素上时 Windows 会自行取整——坐标不对齐会让尺寸被顶偏（`400x100` → `402x102`），尺寸不对齐则会**每次重启长大 1px**（实测 `593x218` → `594x219` → `595x220`…）。按缩放比算出网格步长并对齐后，实测连续重启尺寸完全一致、零漂移。代价是窗口尺寸可能与配置值相差不超过 3px。
- **半透明用 `setOpacity` + 系统材质，而不是透明窗口**：Electron 的 `transparent: true` 窗口**不支持缩放**（官方限制），会造成"窗口不可调整大小"；CSS `backdrop-filter` 也只能模糊页面自身内容，无法模糊窗口下方的桌面。因此改用 `win.setOpacity()` 实现半透明，用 Windows 11 的 `backgroundMaterial: 'acrylic'` 实现真正的高斯模糊，两者都不影响缩放能力。
- **构造窗口后显式 `setBounds` 一次**：在非 100% 缩放的 Windows 上，`BrowserWindow` 构造阶段会把尺寸做 DPI 取整（高度 100 → 103），若直接记录会导致每次启动都长几像素。显式 `setBounds` 一次即可精确落位，实测连续重启尺寸完全一致。
- **拖动结束、缩放结束也会落盘窗口状态**：不只依赖关闭事件，进程被强杀时也不丢状态（缩放结束做了去抖，避免拖拽过程中频繁写盘）。
- **主题色值与窗口底色同源**：避免启动瞬间出现与主题不符的底色闪烁。
- **窗口保持不透明**：保证在 Windows 上边缘缩放稳定可靠（透明窗口的缩放支持不佳）。
- **配置固定在 exe 旁边**：打包后代码被塞进只读的 `app.asar`，配置必须写到外部。`config.yaml` 因此固定在「exe 所在目录」（单文件便携版通过 `PORTABLE_EXECUTABLE_DIR` 定位，而非临时解压目录）。小说资源不打进包内，相对路径一律以该目录为基准，避免"路径到底相对谁"的歧义。
- **读取失败给出可操作的提示**：路径不存在、目录下没有 txt、`source` 留空等都直接显示在阅读窗口里，并回显解析后的路径与配置文件位置，而不是只把原始错误抛给用户。
